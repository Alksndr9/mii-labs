# Библиотека промпт-шаблонов (структура RTCF)

Каждый шаблон построен по схеме **Role → Task → Context → Format**. Части в `{фигурных скобках}` заполняются под конкретную задачу. Шаблоны дополняют файл правил [`rules.md`](rules.md): общие правила проекта уже лежат в `CLAUDE.md`, поэтому в шаблоне описывается только специфика задачи.

| # | Сценарий | Когда использовать |
|---|---|---|
| 1 | Генерация компонента / функции | новая функциональность по описанию |
| 2 | Рефакторинг | код работает, но его трудно читать или расширять |
| 3 | Написание тестов | для существующего кода без тестов |
| 4 | Исправление бага | есть воспроизводимая ошибка |
| 5 | Декомпозиция задачи | задача слишком большая для одного промпта |

---

## 1. Генерация компонента / функции

```markdown
**Role:** Ты — Senior React-разработчик проекта FoodTech.

**Task:** Создай {компонент / функцию} `{Имя}`, который {что делает с точки зрения пользователя}.

**Context:**
- Где используется: {страница / родительский компонент}
- Входные данные: {пропсы / аргументы и их типы}
- Поведение: {список требований, по одному на строку}
- Состояния: {loading / error / empty / success — какие нужны}
- Не делать: {что сознательно не входит в задачу}

**Format:**
1. План: какие файлы создаются и зачем.
2. Код полными файлами с путями.
3. Тест рядом с компонентом (`{Имя}.test.tsx`), минимум позитивный и негативный сценарий.
4. Как проверить вручную.
```

**Пример использования:**

```markdown
**Role:** Ты — Senior React-разработчик проекта FoodTech.

**Task:** Создай компонент `CartSummary`, который показывает итог корзины и кнопку «Оформить заказ».

**Context:**
- Где используется: страница `/cart`, правая колонка (на мобильных — внизу экрана)
- Входные данные: `total: OrderTotal` (subtotal, durationDiscount, promoDiscount, delivery, total — в копейках), `onCheckout: () => void`, `isSubmitting: boolean`
- Поведение: строки скидок показываются, только если скидка > 0; «Доставка: бесплатно», если delivery = 0
- Состояния: при isSubmitting кнопка заблокирована и показывает спиннер
- Не делать: ввод промокода (будет отдельным компонентом)

**Format:**
1. План: какие файлы создаются и зачем.
2. Код полными файлами с путями.
3. Тест `CartSummary.test.tsx`: отображение скидок, бесплатная доставка, блокировка кнопки.
4. Как проверить вручную.
```

## 2. Рефакторинг кода

```markdown
**Role:** Ты — ревьюер кода и специалист по рефакторингу React/TypeScript.

**Task:** Отрефактори `{путь к файлу}`, не меняя внешнее поведение.

**Context:**
- Проблемы, которые я вижу: {длинный компонент / дублирование / смешаны логика и UI / ...}
- Цель: {вынести логику в хук / разбить на компоненты / убрать дублирование / ...}
- Ограничения: публичный API (пропсы, экспорт) не меняется; существующие тесты должны проходить.

**Format:**
1. Список найденных проблем с пояснением, почему это проблема.
2. План рефакторинга по шагам.
3. Итоговый код полными файлами.
4. Подтверждение: какие тесты запущены и результат.
```

**Пример использования:**

```markdown
**Role:** Ты — ревьюер кода и специалист по рефакторингу React/TypeScript.

**Task:** Отрефактори `src/features/catalog/MealCard.tsx`, не меняя внешнее поведение.

**Context:**
- Проблемы, которые я вижу: компонент 150 строк, в нём выбор срока, расчёт цены и анимация кнопки
- Цель: вынести выбор срока в `DurationPicker`, расчёт цены — в чистую функцию `getMealPrice`, анимацию кнопки — в хук `useTemporaryFlag`
- Ограничения: пропсы `MealCard` не меняются; тесты `MealCard.test.tsx` должны проходить.

**Format:**
1. Список найденных проблем с пояснением, почему это проблема.
2. План рефакторинга по шагам.
3. Итоговый код полными файлами.
4. Подтверждение: какие тесты запущены и результат.
```

## 3. Написание тестов для существующего кода

```markdown
**Role:** Ты — QA-инженер, пишущий автотесты на Vitest и React Testing Library.

**Task:** Напиши тесты для `{путь к файлу}`.

**Context:**
- Что делает код: {кратко}
- Важные сценарии: {позитивные — что должно работать}
- Граничные случаи: {пустые данные, ошибки, предельные значения}
- Что мокать: {API / таймеры / роутер}; что не мокать: {чистые функции}

**Format:**
1. Таблица тест-кейсов: сценарий → ожидаемый результат.
2. Файл `{имя}.test.ts(x)` полностью.
3. Результат запуска `npx vitest run {путь}`.
```

**Пример использования:**

```markdown
**Role:** Ты — QA-инженер, пишущий автотесты на Vitest и React Testing Library.

**Task:** Напиши тесты для `src/features/cart/lib/calculateOrderTotal.ts`.

**Context:**
- Что делает код: считает сумму заказа со скидкой за срок, промокодом и доставкой
- Важные сценарии: заказ на 1 день без скидок; скидка 5% за 5 дней и 10% за 7 дней
- Граничные случаи: пустая корзина; сумма ровно 5000 ₽ (порог бесплатной доставки); промокод больше суммы заказа
- Что мокать: ничего — это чистая функция

**Format:**
1. Таблица тест-кейсов: сценарий → ожидаемый результат.
2. Файл `calculateOrderTotal.test.ts` полностью.
3. Результат запуска `npx vitest run src/features/cart`.
```

## 4. Исправление ошибок и багов

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину бага, а не маскирует симптом.

**Task:** Найди и исправь ошибку: {краткое описание}.

**Context:**
- Шаги воспроизведения: {1, 2, 3}
- Ожидаемое поведение: {...}
- Фактическое поведение: {...}
- Ошибка из консоли / лог: {вставить текст или приложить скриншот}
- Где, вероятно, проблема: {файл, если известен}

**Format:**
1. Причина бага: что именно и почему происходит.
2. Исправление: diff или полный файл.
3. Регрессионный тест, который падал до исправления и проходит после.
```

**Пример использования:**

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину бага, а не маскирует симптом.

**Task:** Найди и исправь ошибку: при смене срока рациона цена в корзине не обновляется.

**Context:**
- Шаги воспроизведения: 1) добавить «Баланс» на 1 день; 2) открыть корзину; 3) сменить срок на 7 дней
- Ожидаемое поведение: сумма меняется с 1 490 ₽ на 9 387 ₽ (7 дней −10%)
- Фактическое поведение: сумма остаётся 1 490 ₽, хотя в селекторе выбрано «7 дней»
- Ошибка из консоли: нет ошибок
- Где, вероятно, проблема: `src/features/cart/useCart.ts`

**Format:**
1. Причина бага: что именно и почему происходит.
2. Исправление: diff или полный файл.
3. Регрессионный тест, который падал до исправления и проходит после.
```

## 5. Декомпозиция сложной задачи на подзадачи

```markdown
**Role:** Ты — техлид, который планирует работу для AI-агента.

**Task:** Разбей задачу «{формулировка}» на подзадачи, каждая из которых выполняется одним промптом.

**Context:**
- Цель с точки зрения пользователя: {...}
- Что уже есть в проекте: {готовые компоненты, API, таблицы}
- Ограничения: {сроки, стек, что нельзя менять}

**Format:**
Нумерованный список подзадач. Для каждой:
- что сделать (1–2 предложения);
- результат, по которому понятно, что подзадача выполнена (файл, тест, экран);
- от каких подзадач зависит.
В конце — порядок выполнения и какие подзадачи можно делать параллельно.
```

**Пример использования:**

```markdown
**Role:** Ты — техлид, который планирует работу для AI-агента.

**Task:** Разбей задачу «Оформление заказа с оплатой» на подзадачи, каждая из которых выполняется одним промптом.

**Context:**
- Цель с точки зрения пользователя: из корзины ввести адрес, выбрать дату доставки и оплатить
- Что уже есть в проекте: каталог, корзина, `calculateOrderTotal`, таблицы `meals` и `orders` в Supabase
- Ограничения: оплата пока в тестовом режиме, свой бэкенд не пишем — только Supabase

**Format:**
Нумерованный список подзадач. Для каждой:
- что сделать (1–2 предложения);
- результат, по которому понятно, что подзадача выполнена (файл, тест, экран);
- от каких подзадач зависит.
В конце — порядок выполнения и какие подзадачи можно делать параллельно.
```
