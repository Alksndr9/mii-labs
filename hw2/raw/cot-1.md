# Шаг 1. Разбор требований к расчёту стоимости заказа

## 1. Входные данные

**Позиция корзины (`CartItem`)**
| Поле | Тип | Ограничения |
|---|---|---|
| `dietId` | `string` | идентификатор рациона |
| `pricePerDay` | `number` | цена за день в копейках, целое ≥ 0 |
| `days` | `1 \| 5 \| 7` | только эти значения |
| `quantity` | `number` | целое ≥ 1 |

**Промокод (`Promo`), необязательный.** Это размеченное объединение:
- `{ kind: 'percent', percent: number }`, где 0 < percent ≤ 100;
- `{ kind: 'fixed', amount: number }`: сумма в копейках, целое > 0.

**Константы бизнес-правил** (выносятся в `UPPER_SNAKE_CASE`, чтобы не дублировать «магические числа»):
- `DURATION_DISCOUNT = { 1: 0, 5: 5, 7: 10 }` в процентах;
- `DELIVERY_FEE = 30_000` (300 ₽);
- `FREE_DELIVERY_THRESHOLD = 500_000` (5000 ₽).

**Выход.** Не одно число, а разбивка для UI и чека: `subtotal` (сумма без скидок), `durationDiscount`, `promoDiscount`, `delivery`, `total`. Все значения в копейках.

## 2. Порядок расчёта

1. **Сумма строки:** `pricePerDay × days × quantity`.
2. **Скидка за срок для каждой строки.** Она зависит от `days` конкретной позиции. По сути это цена товара «рацион на 7 дней», а не скидка на заказ. Поэтому она применяется первой и к каждой строке отдельно, ведь в корзине могут быть позиции с разным сроком.
3. **Сумма товаров после скидки за срок.** Здесь же проверяется порог бесплатной доставки.
4. **Промокод** применяется к сумме из п. 3 и только к товарам, не к доставке. Скидка ограничивается сверху суммой товаров, поэтому итог за товары не уходит в минус.
5. **Итог:** товары после промокода плюс доставка.

**Почему промокод идёт после скидки за срок:**
- Фиксированный промокод не перестановочен с процентной скидкой. Если вычесть 500 ₽, а потом 10%, клиент получит больше, чем при обратном порядке. Стандартная практика: сначала «цена товара», потом маркетинговые скидки поверх фактической цены.
- Процентный промокод математически перестановочен со скидкой за срок, но порядок всё равно должен быть фиксированным, чтобы копейки при округлении считались одинаково.

**Почему порог доставки проверяется до промокода:** иначе возникает парадокс. Пример: товары на 5000 ₽, промокод −100 ₽. Если считать порог после промокода, то 4900 + 300 = 5200 ₽, и **применение промокода увеличивает итог**. Если проверять порог до промокода, промокод никогда не ухудшает цену для клиента.

## 3. Граничные случаи

**Деньги и округление**
- Процентные скидки дают дробные копейки. Округляем `Math.round` до целой копейки: скидку за срок на уровне строки, процент промокода один раз от суммы. Тогда строки в чеке сходятся с итогом.
- `Number.MAX_SAFE_INTEGER` для реальных сумм не достижим, `BigInt` не нужен.

**Порог доставки**
- Ровно 500 000 копеек: доставка бесплатная («от 5000» трактуем включительно).
- 499 999 копеек: доставка 300 ₽.
- Сумма ниже порога из-за скидки за срок (без скидки 5200 ₽, со скидкой 4680 ₽): доставка платная, порог считается по сумме после скидки за срок.

**Промокод**
- Фиксированный промокод больше суммы товаров: скидка равна сумме товаров, товары стоят 0, доставка остаётся.
- `percent = 100`: товары бесплатны, доставка по правилу порога.
- `percent ≤ 0`, `percent > 100`, `amount ≤ 0`, дробные значения: ошибка валидации.
- Промокода нет: `promoDiscount = 0`.

**Корзина**
- Пустая корзина: все поля 0, доставка 0. Оформить заказ всё равно нельзя, а показывать «доставка 300 ₽» при пустой корзине странно.
- Один рацион с разными сроками (на 5 и на 7 дней): это разные строки с разными скидками.
- `quantity` 0, отрицательное или дробное: ошибка.
- `days` вне {1, 5, 7}: ошибка. Тип это ограничивает, но данные приходят из Supabase и `localStorage`, поэтому нужна проверка во время выполнения.
- `pricePerDay = 0` (например, пробный рацион) допустим, `pricePerDay < 0` — ошибка.

## 4. Неясные вопросы и принятые допущения

| Вопрос | Допущение |
|---|---|
| Порог 5000 ₽ считается до или после скидок? | После скидки за срок, но **до промокода** (см. парадокс выше). |
| Распространяется ли промокод на доставку? | Нет, только на товары. |
| Можно ли промокодом обнулить товары? | Да, товары ≥ 0. Итог ≥ 0 гарантирован, потому что доставка ≥ 0. |
| Суммируется ли промокод со скидкой за срок? | Да, последовательно, как описано в разделе 2. |
| Сколько промокодов можно применить? | Один. |
| Как округлять? | `Math.round` до копейки: скидку за срок по строке, промокод от суммы. |
| Порог «от 5000» включительный? | Да, `>=`. |
| Срок действия, минимальная сумма, лимиты промокода? | Вне этой функции. Она получает уже проверенный промокод, проверку делает сервер. |
| Как сообщать о некорректных данных? | Бросать `Error` с понятным сообщением, потому что это ошибка программиста или порча данных, а не пользовательский сценарий. Ошибки неверного промокода обрабатываются выше, в UI. |
| Где источник истины? | Клиентская функция нужна только для показа цены. Итоговую сумму к оплате **обязательно** пересчитывает сервер (Supabase RPC/Edge Function), иначе клиент может её подменить. |
